# 知乎文章写作与发布

把内容整理、平台排版和发布结果一起完成。用户明确要求发布时，完成编辑与预览后直接发布；用户要求先审稿或仅保存草稿时，停在相应阶段。调用本 skill 不等于授权发布所有后续内容，也不授权分享到想法、圈子、私信或其他平台。

## 确定内容与操作范围

- 阅读用户给出的原文、文件或对话链接。无法访问原文时说明缺口，不把自行写作冒充原文整理。
- 新文章、更新已有文章、保存草稿是不同操作。更新时使用用户指定的文章；已有当前任务草稿则继续使用，避免创建重复文章。
- 有完整成稿时以排版为主，除非用户要求，不大幅改写。只有主题时再撰写。长度、读者和结构可以根据材料合理判断，只有影响实质结果的缺口才提问。
- 延续用户已经表达的要求。默认中文技术文章的写作偏好是：逻辑清楚、公式完整、逐步推导、图解充分、自然朴素，避免模板化口吻。

## 内容与本地稿

- 技术文章按概念依赖组织：问题与直觉、符号及假设、推导、例子、实现与边界。按内容调整，不强行套固定章节数。
- 检查公式的维度、索引、归一化范围、初始条件和边界。区分数学等价、浮点误差与工程性能结论。重要数值例子可计算核对；算法推导必要时用小规模参考实现验证。
- 需要来源核对时优先论文、官方文档与作者实现，正文保留可点击来源。不要编造实验、引用、性能数据或个人经历。
- 图应解释状态变化、数据流、分块、形状或对照；数量取决于需要。数学图优先程序化生成以保证标注精确。检查中文字体、公式符号、分辨率和缩小后的可读性。
- 在工作目录保存可恢复的正文与图片。含大量公式时，提供带渲染公式和嵌入配图的离线 HTML 很有用；Markdown 源码与图片可一并交付。遵循当前环境的 outputs/work 路径约定。

## 选择发布通道与登录

- 先发现当前实际可用的知乎连接器或 MCP 能力；只有其支持所需的正文、图片、公式和结果核验时才优先使用。用户未指定通道时，可直接用浏览器完成。
- 不因用户提到某个 GitHub 项目就安装运行它；先检查能力是否合适。不要把不明字符串当作可用 MCP 配置，也不要把用户凭证复制到文章、skill、日志或交付包。
- 浏览器操作使用当前环境支持的浏览器工具及其文档。禁止用页面脚本调用隐藏 API、修改应用内部状态或绕过正常编辑器流程。
- 检查实际操作会话是否已登录。外部 Chrome 或手机 App 登录不等于当前内置浏览器已登录。需要登录时把知乎页交给用户，明确让用户在**这张操作页面**完成扫码/登录；恢复后确认编辑器或账号 UI 已出现。
- 不默认提取或导出浏览器 Cookie。日常发布优先复用正常登录会话；登录失效时再请用户在该会话登录。遵守当前工具对验证码和认证操作的要求。

## 在知乎编辑并检查

使用浏览器导入、公式、图片或预览时，先阅读 [references/browser-workflow.md](references/browser-workflow.md)。其中记录实际遇到的平台行为；选择器、菜单和登录状态必须重新观察。

1. 保存本地稿后进入写文章入口，记录本次草稿地址以便恢复。
2. 标题单独填写；正文避免再次出现重复文章标题。导入或粘贴后核对段落、标题层级、列表、表格、代码、行内与独立公式。
3. 把图放在对应解释附近，加必要图注。确认所有图已上传，失败项单独重试。
4. 按文章选择合适封面与少量技术话题。若平台提供创作声明，按实际创作方式如实选择；AI 辅助撰写应选择相应选项。自然文风不意味着隐瞒创作方式。
5. 确认保存完成，再通过平台预览抽查首尾、长公式、矩阵、表格、代码和配图。必要时分段滚动等待懒加载，区分暂未渲染与真实丢失。
6. 用户已明确要求发布且没有额外审稿约束时，完成检查就发布，无需再问一次。用户要求审核则交付具体可审阅稿件，等待其意见。

## 完成与异常处理

- 点击发布不是完成。等待明确成功提示或已发布页面，记录真实文章链接。审核中就写“已提交，审核中”，不宣称已经公开可见。
- 发布等待较长时，观察当前状态和错误。结果不明确时先核查本篇文章状态，不另建文章盲目重试。无法确认时保留草稿和本地文件，明确说明阻塞点。
- 一次明显的可恢复失败可针对性重试；同一步连续失败两次且没有新证据时，保留成果并切换受支持路径或请求必要协助。不要反复提交、删除或重建内容。
- 除用户指定之外，不修改旧文章，不清空其他草稿，不触发发布后的转发或私信分享。
- 根据浏览器工具要求保存成功凭证和完成摘要。最终给文章链接、简短内容说明与本地备份；只有平台确认成功时才写“已发布”。
